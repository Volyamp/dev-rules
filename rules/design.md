# 設計（要件定義・ADR・設計の確定）

## 3. 要件定義のとき
- docs/ARCHITECTURE.md は次の4項目で書く。
  1. 目的・要件
  2. 技術選定
  3. 全体構成・設計方針
  4. 進捗・引き継ぎメモ
- 「1. 目的・要件」には、テストの根拠になるよう次を具体的に書く（1-4）。
  - 入力の形式と範囲（例：名前は1〜20文字、空欄不可）
  - 範囲外の入力のときの動き（例：「入力エラー」と表示して終了）
  - 出力の形式（例：「追加しました（ID: 1）」）
  - ※雛形の（例）は書き方の見本であり、提案ではない。プロダクトに合わせて書き直す。
- AI が提案した数値や細かい動きには「（提案・要確認）」と付ける。人間が OK を出したら「（確定）」に直す。
- 決まっていないことは決めずに「未決定」と書く。
- 「（確定）」の印は項目（行）ごとに付ける。確定の状態の正本はこの印であり、進捗メモに確定項目の一覧は書かない。
- 人間がチャットで「確定」と言ったときは、P2 を使わなくても確定にしてよい（v7）。その場合、AI は確定にした項目を返答の冒頭に一覧で書き、違うと言われたら戻す。確定にしたら、その場で枝にコミットして push する。
- 書き終えたら人間の確認を待つ。OK が出るまでコードは書かない。
- 区切り（コミットする時点、または依頼文の作業が終わる時点）ごとに進捗メモを更新する。

## 4. 決めたことの記録（ADR）
- 会話の内容そのものは残さない。
- 大きな決定は、docs/adr/ に ADR として残す。書き方は adr-template.md に従う。
- 大きな決定とは、次のどれか。
  - 言語、ライブラリ、データの保存先、実行環境、外部サービスの選択
  - 「（確定）」済みの要件の変更
  - 作らない・やめると決めたこと
- ADR の番号は消さない・詰め直さない。変えるときは、新しい番号で「○○番を置き換え」と書き、古い方の状態を「○○番で置き換え」に変える。
- AI は状態を「提案」にして下書きまで行い、枝にコミットする。人間が OK を出したら「確定」にする（依頼文 P2 を使うか、チャットで確定と言う。§3）。
- ARCHITECTURE の「2. 技術選定」には、選んだ理由を書かず、ADR の番号だけを書く（二重記録を避ける）。

## 要件定義（設計メモ作成）
- 雛形の docs/ARCHITECTURE.md を埋める。1〜3 を書く（rules/design.md §3）。
- 人間が書いた「作りたいもの」の説明だけを根拠にする。説明にないことは「未決定」にする。AI の提案には「（提案・要確認）」を付ける。
- CLAUDE.md の「製品名」も書く。
- 進捗メモを更新する。
- コミットして push し、人間の確認を待つ。OK が出るまでコードは書かない。
- この枝は、下書きを main に入れるためのもの。「（確定）」は1つも無いので、人間が取り込んでも安全。

## 設計の確定
- 人間が指定した項目を「（確定）」にする。直す項目は直して「（提案・要確認）」に戻す。
- 大きな決定（rules/design.md §4）があれば、ADR を「提案」で下書きする。人間が指定した ADR は「確定」にする。
- 1〜3 がすべて「（確定）」になったら、進捗メモの「今の段階」を「実装中」にする。そうでなければ「設計の確認待ち」にする。
- 人間がチャットで確定と言った項目も、確定にする（P2 を使わなくてもよい。rules/design.md §3）。確定にした項目は、返答の冒頭に一覧で書く。
- 設計の枝（design/draft）を同じブランチで更新し続ける。人間が確定を指定したら、確定を push して止まる。取り込みは人間が行う。
