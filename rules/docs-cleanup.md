# 文書の整理

## 文書の整理
きっかけ：人間が依頼したとき（任意のタイミング）。AI が自発的に行うのは、PR を依頼されたときの、PR を作る前だけ。依頼文は prompts P13。

### 持ち主の表（どの事実をどの文書に置くか）
| 種類 | 置く文書 | 書くこと | 書かないこと |
|---|---|---|---|
| 要件・確定事項 | ARCHITECTURE 1〜3 | 目的、要件、技術、構成、（確定）の項目 | 決めた理由（ADR へ） |
| 決定と理由 | ADR | 決定、理由、代替案、状態 | 今の作業の状態 |
| 使い方・実際の動き | README | 実装に基づく使い方。末尾に差分 | 未実装の予定 |
| 今の状態 | ARCHITECTURE §4（進捗メモ）の引き継ぎ部分 | 段階、基点の SHA と枝、作業中の PR、未解決の問題、次の一歩、未確認、レビューの件数と未対応の一覧 | 完了した作業の詳細（git の履歴へ） |
| 静的レビュー | docs/reviews/ | 指摘と対象の SHA | 修正の進捗（引き継ぎには件数と SHA だけ） |

### 手順
1. **棚卸し**：対象のすべての文書から、事実を含む文を抜き出す（段階、次の作業、決定、使い方、差分、レビュー、未確認）。元のファイルと節を控える。
2. **配置**：それぞれの事実を、上の表で持ち主の文書に割り当てる。
3. **振り直す**：持ち主の文書に書く（すでにあれば更新する）。持ち主以外にある同じ事実は、「○○を見よ」の参照に置き換える。
4. **突き合わせ**：正本の内容を、実装、git、CI で確かめる。確かめられないものは「未確認」と書き、推測で埋めない。
   - （確定）の項目は変えない（rules/impl.md §5）。
   - ARCHITECTURE に、時間とともに増える内容（完了した作業の詳細、履歴、古い段階、古い決定）が残っていれば、持ち主へ移す。
5. **引き継ぎ**：ARCHITECTURE §4（進捗メモ）の引き継ぎ部分を、次の内容で上書きする。
   - 整理が見た実装の HEAD の SHA（整理のコミットより前のもの）と、枝の名前
   - 作業中の PR（PR を作ったときだけ。「PR #n（マージ待ち）」と書く）
   - 未解決の問題（あれば。最優先のものを先頭に）
   - 次にやること（1〜3件）
   - 未確認・未決定の一覧（件数と内容）
   - テストの結果（確かめられたものだけ）
   - レビューの件数と、未対応のものの一覧（対象の SHA）
6. **確かめ**：「未確認」「未決定」「（要確認）」を grep し、残るものを一覧にする。同じ事実が2か所に残っていないかを確かめる。`git diff` で、（確定）の行が変わっていないことを確かめる。
7. **報告**：変えた文書と節、移した事実の一覧（元の場所 → 新しい場所）、残った未確認の一覧（件数と内容）、確かめられなかったこと。変えたものがなければ「変更なし」と報告し、コミットしない。
8. **コミット**：今の枝に「整理：〇〇」として分けて入れ、push する。main には入れない。

### 次のセッションでの確認
引き継ぎ部分の SHA と、`git log --oneline <SHA>..HEAD` の結果を比べる。整理のコミットは実装を変えないので、差分が整理のコミットだけなら、引き継ぎ部分をそのまま信じて作業に入る。実装のコミットが増えていれば、その差分だけを見る。
