# 実装（作業ルール・実装・README）

## 5. 作業ルール
- すべての変更（設計書、ADR、README、レビュー、テスト、コード）は、main に直接書き込まない。用途を表す接頭辞（design/、impl/、docs/、test/、fix/、adr/）で始まるブランチで行い、コミットして push する（PR は原則作らない。common-rules §3）。
- コミットして push するところまでが AI の仕事。PR は、依頼者が依頼したときだけ AI が作る。マージは人間が行い、AI はマージしない。
- 規則や手順を変えるときは、VERSION を上げ、README の変更履歴に1行書く。同じ内容を書いているすべての文書（common-rules、rules/、prompts.md、setup.md、README.md、dynamic-test.md、VERSION、claude-md-block.md、product-template の CLAUDE.md）を検索し、食い違いを残さない。残す場合は、理由をコミットメッセージに書き、人間の確認を取る。
- 依頼された範囲を狭めるとき（一部だけで作業を終えるとき）は、先に人間に確認する。AI の判断で範囲を分けない。
- 人間が実行したり使ったりするファイル（スクリプト、設定、手順書など）は、作成した時点で、添付（SendUserFile 等）か、人間が取り込める枝（リポジトリ）で届ける。作業用フォルダ（scratchpad や一時フォルダ）のパスだけを伝えない。人間の環境からは開けないため。
- 次の新しいチャットには、main ではなく、対象の枝の名前を渡す。GitHub をつながないチャット（テスト作成）は、貼る資料で渡す。
- 書き込み権限がない環境では、patch や全文の貼り付けを使わず、AI が枝にコミットして、その枝を git bundle にして出す（枝の名前、基点の SHA、sha256 を添える）。bundle と同じ返答に、取り込みコマンド（`git fetch <bundle>(ファイル名のみ) <枝>:<枝>` と `git push -u origin <枝>`）を書く。人間は取り込んで push する。main には置かせない。GitHub をつながないチャット（P5）は、ファイル名と全文を出す。
- コミットメッセージには、対応する ARCHITECTURE.md の節、変更理由、進捗メモを更新したかを書く。
- 要件や設計を変えるときは、先に docs/ARCHITECTURE.md を更新（提案）し、人間の承認（確定）を得てから実装する。
- 「（確定）」の項目に反する実装はしない。反する必要が出たら、そこで止まって人間に確認する。
- 実装中に気づいた「ARCHITECTURE と違う点」や「書かれていない細部の決め方」は、進捗メモの「実装とのずれ」に書く。README 作成のときに、README 末尾の「ARCHITECTUREとの差分」に移す（rules/impl.md「README作成」）。
- 実装と同じ区切りのコミットに、進捗メモの更新を含める。
- 次のものは、人間の明確な指示がない限り変更しない。
  - .github/ 以下（workflows、CODEOWNERS）
  - .env などの秘密情報ファイル
  - ARCHITECTURE.md の「（確定）」の項目
- 「明確な指示」とは、依頼文に、そのファイルや項目を変えてよいと書いてあること。（prompts P2 は「（提案・要確認）→（確定）」の書き換えを、P6 は ci.yml の変更を、それぞれ許可している。）

- 文書の整理は、rules/docs-cleanup.md「文書の整理」に従う。人間が依頼したときは、いつでも行う。AI が自発的に行うのは、PR を依頼されたときの、PR を作る前の整理だけ。
- PR を作った時点の状態は、「PR #n（マージ待ち）」と書く。マージ済みかどうかはドキュメントに書かず、PR の一覧（マージ状態）で確認する。
- マージ後に、ドキュメントだけを変えるための push はしない。次の PR を作る整理の時点で、前回分の状態を更新し、完了した項目は履歴に任せる。

## 実装
- 始める条件は common-rules §2。足りなければ止まる。
- 作業は impl/《内容》で行い、コミットして push する（PR は原則作らない。依頼者が依頼したときだけ作る）。枝の決まりは common-rules §3。
- 進捗メモを同じ枝・同じ区切りで更新する。区切りごとのコミットに含めて push する（common-rules §3、v7）。
- 「（確定）」に反する実装が必要になったら、止まって確認する。
- 確定していない細部や、書かれていない細部は、進捗メモの「実装とのずれ」に書く。
- README も同じ枝で作る（「README作成」の節）。
- 終わったら、push した枝の名前と次の一手（P7：静的レビュー。この枝を指定）を伝える。

## README作成
- 実装を読んで、実際の動きだけを書く（理想や予定は書かない）。
- 項目：概要／セットアップ／実行方法（実行できるコマンドの形で）／ディレクトリ構成／主要な機能と使い方／既知の制約・未実装部分／ARCHITECTUREとの差分
- 「主要な機能と使い方」には次を必ず書く。
  - 実際に打つコマンド（そのままコピーして使える形）
  - 入力の例
  - 出力の例（実際に実行して得たもの。実行できなければ、コード内の表示文から書き、「未実行・コードより」と明記する）
  - 入力を間違えたときに表示されるメッセージ（コードから読み取れる範囲）
- 末尾の「ARCHITECTUREとの差分」には、進捗メモの「実装とのずれ」と、実装を読んで見つけた違いをまとめる。
  - 優先順位：ARCHITECTURE の「（確定）」が正。README の本文は、実装の実際の動き。
  - 差分に載せた箇所は、テストの対象外になる（rules/test.md §6）。
  - 「（確定）」に反する実装を見つけたら、README に書くだけでなく、実装のバグの可能性として人間に報告する。
- 出力：README.md（実装の枝に入れる）
