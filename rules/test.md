# テスト（作成・取り込み・失敗時の切り分け）

## 6. テスト
- 根拠は、README.md の「主要な機能と使い方」と、ARCHITECTURE.md の「（確定）」の項目だけ。
- README 末尾の「ARCHITECTUREとの差分」に載っている箇所は、テスト対象外。
- テスト作成のチャットは、貼られた資料だけを読む。貼られていないソースコード（src/ など）は読まない。
- 仕様に書かれていない「動き」は、テストを書かず「仕様不明のため未作成」と書く。
  - 「動き」とは、戻り値の型、エラーの種類や文言、数値の範囲、出力の形式など。
- 関数名・コマンド名・引数名の推測は、書いてよい。推測した名前は tests/adapter.* の1ファイルにまとめ、ファイルの先頭と各テストの説明に「推測である」と書く。
- テストの期待値（assert）は、仕様から決める。実装に合わせて変えない。
- 質問するより先に、書ける範囲のテストを作る。
- テストは CI で実行する。失敗したときは rules/test.md「テストが失敗したとき」に従う。
- README と ARCHITECTURE の「（確定）」が食い違うときの扱いは、prompts P5 の【前提】に従う（ARCHITECTURE が正）。
- テスト作成の【前提】など、貼る文章の正本は prompts P5。ここには複製しない。

## テスト作成
- 別の新しいチャットで、GitHub をつながずに行う。
- 前提、資料、作るもの、最後に付けるもの、の文章は prompts P5 が正本。ここには書かない。
- 出力は、tests/ に置くファイルの全文（adapter を含む）。
- 出力されたテストは、次の「テストの取り込み」でリポジトリに入れる。
- 「仕様不明のため未作成」が多いときは、仕様（ARCHITECTURE、README）の不足として人間に返す。

## テストの取り込み
- 別の新しいチャット（GitHub あり）で、prompts P6 を使う。
- tests/ に、貼られたテストをそのまま置く。期待値は変えない。
- .github/workflows/ci.yml の TEST_COMMAND とセットアップ手順を、ARCHITECTURE の「2. 技術選定」に合わせて設定する（P6 が、この変更の明確な指示）。
- テストを実行できれば、結果をそのまま報告する。失敗しても、ここでは直さない。
- テストの枝（test/《内容》。例：test/todo-list）にコミットして push する。進捗メモの「テスト」を更新する。

## テストが失敗したとき
失敗の原因を、次の4つのどれかに切り分ける。判断がつかないときは、直さず「判断不能」として人間に報告する。

| 切り分け | 意味 | 直し方 |
|---|---|---|
| ① 実装のバグ | 仕様どおりのテストが、実装のせいで落ちる | 実装を直す。tests/ の期待値は変えない（P10） |
| ② 名前の不一致 | 推測した関数名・コマンド名・引数名が実装と違う | tests/adapter.* だけを直す（P10）。直す人は、README と公開されている名前だけを見る。値の変換・判定は入れない。切り分けを人間が確認してから直す |
| ③ 期待値の誤り | テストが仕様を読み違えている | 直さず報告。テスト作成のチャットに、失敗のログを付けて戻す（P5） |
| ④ 仕様の誤り・不足 | 仕様自体が間違い、または足りない | 実装もテストも直さず報告。ARCHITECTURE を更新（P2）してから①か③へ |
